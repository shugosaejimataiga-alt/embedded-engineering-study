# 1. ソースコードから実行ファイルができるまで

C言語で作成したソースコードは、そのままではCPUが実行できない。

通常、GCCでは次の4つの工程を経て実行ファイルを生成する。

1. 前処理（プリプロセッサ）
2. コンパイル（コンパイラ）
3. アセンブル（アセンブラ）
4. リンク（リンカ）

## 処理の流れ

```text
main.c（C言語のソースコード）
    ↓
① 前処理（プリプロセッサ）
    ↓
展開済みソースコード
    ↓
② コンパイル（コンパイラ）
    ↓
main.s（アセンブリ言語）
    ↓
③ アセンブル（アセンブラ）
    ↓
main.o（オブジェクトファイル）
    ↓
④ リンク（リンカ）
    ↓
main.exe（実行ファイル）
```

※ この流れはGCCの一般的な処理を簡略化したもの。

GCCは通常、これらの工程をまとめて実行できる。

---

# 2. 前処理（プリプロセッサ）

## 2-1. 前処理とは

前処理とは、C言語のソースコードをコンパイルする前に行う処理。

プリプロセッサは、主に `#` で始まる指示を処理する。

代表的な指示は次のとおり。

- `#include`：指定されたファイルの内容を取り込む
- `#define`：マクロを定義する
- `#ifdef`：マクロが定義されているかを判定する
- `#ifndef`：マクロが定義されていないかを判定する
- `#endif`：条件付きコンパイルの範囲を終了する

前処理では、ヘッダーファイルの取り込み、マクロの展開、条件付きコンパイルなどを実行する。

この段階では、まだ機械語への変換は行われていない。

## 2-2. #include の処理

例：config.h

```c
#define MAX_SPEED 100
```

例：main.c

```c
#include "config.h"

int main(void)
{
    int speed = MAX_SPEED;

    return 0;
}
```

前処理では、まず `config.h` の内容が取り込まれる。

さらに、`MAX_SPEED` というマクロが `100` に置き換えられる。

結果として、概念的には次のコードになる。

```c
int main(void)
{
    int speed = 100;

    return 0;
}
```

## 2-3. 前処理の重要ポイント

- プリプロセッサはコンパイル前の処理を担当する。
- `#include` は指定されたファイルの内容を取り込む。
- `#define` はマクロを定義し、使用箇所を展開する。
- `#ifdef` や `#ifndef` は条件に応じてコードを含めるか判断する。
- 前処理の段階では、まだ機械語になっていない。

---

# 3. コンパイル（コンパイラ）

## 3-1. コンパイルとは

コンパイルとは、前処理が終わったC言語のコードを解析し、アセンブリ言語へ変換する工程。

コンパイラは主に次の処理を行う。

1. C言語の文法を確認する。
2. 変数や式、関数などの型を確認する。
3. 必要に応じてエラーや警告を出す。
4. コードの最適化などを行う。
5. アセンブリ言語へ変換する。

## 3-2. アセンブリ言語とは

アセンブリ言語とは、CPUが実行する機械語に近い低水準言語。

CPUの命令を、人間が読める記号や命令名で表現する。

C言語よりもCPUの命令に近い形式である。

## 3-3. コンパイルの例

main.c

```c
int main(void)
{
    int speed = 100;

    return 0;
}
```

GCCでアセンブリファイルを生成する。

```bash
gcc -S main.c -o main.s
```

コマンドの意味：

- `gcc`：GCCを使用する。
- `-S`：アセンブリ言語への変換まで実行して停止する。
- `main.c`：変換対象のソースファイル。
- `-o main.s`：出力するファイル名を指定する。

実行すると、通常は `main.s` が生成される。

ただし、この段階ではまだ実行ファイルではない。

## 3-4. コンパイルの重要ポイント

コンパイラの役割は、C言語の文法や型などを確認し、アセンブリ言語へ変換すること。

文法に問題がある場合はコンパイルエラーが発生する。

型の不一致などについては、エラーになる場合と警告になる場合がある。

---

# 4. アセンブル（アセンブラ）

## 4-1. アセンブルとは

アセンブルとは、アセンブリ言語を機械語へ変換する工程。

この処理を行うプログラムをアセンブラという。

アセンブラは、機械語などを含むオブジェクトファイルを生成する。

## 4-2. 機械語とは

機械語とは、CPUが実行する命令を表す形式。

CPUの種類によって、使用する機械語の命令体系は異なる。

## 4-3. オブジェクトファイルとは

オブジェクトファイルとは、コンパイル・アセンブルされた機械語や、リンクに必要な情報などが格納されたファイル。

一般的な拡張子は `.o`。

Windowsの開発環境では `.obj` が使われることもある。

オブジェクトファイルには、主に次の情報が含まれる。

- 機械語に変換された処理
- 関数や変数などのシンボル情報
- 他のファイルで定義された関数などへの参照情報
- リンク時に必要な再配置情報

オブジェクトファイルは、通常、それだけでは実行できない。

実行ファイルを完成させるにはリンクが必要になる。

## 4-4. アセンブルの例

```bash
gcc -c main.s -o main.o
```

コマンドの意味：

- `gcc`：GCCを使用する。
- `-c`：リンクせず、オブジェクトファイルを生成する。
- `main.s`：入力するアセンブリファイル。
- `-o main.o`：出力するファイル名。

実行すると `main.o` が生成される。

## 4-5. アセンブルの重要ポイント

- アセンブラはアセンブリ言語を機械語へ変換する。
- オブジェクトファイルを生成する。
- オブジェクトファイルにはリンクに必要な情報も含まれる。
- `.o` ファイルは通常、そのまま実行できない。

---

# 5. リンク（リンカ）

## 5-1. リンクとは

リンクとは、オブジェクトファイルやライブラリを使って、関数や変数などの参照先を解決し、実行ファイルを生成する工程。

この処理を行うプログラムをリンカという。

リンカの主な役割：

1. 複数のオブジェクトファイルを結合する。
2. 関数や変数などの参照先を解決する。
3. 必要なライブラリと結びつける。
4. 必要なアドレス調整などを行う。
5. 実行ファイルを生成する。

注意点：

リンカは関数の宣言や引数そのものを組み合わせるわけではない。

関数の呼び出し先や変数の参照先などを解決する。

---

# 6. 複数ファイルをリンクする例

## 6-1. ファイル構成

```text
project/
├── main.c
├── calc.c
└── calc.h
```

## 6-2. calc.h

関数の宣言を記述する。

```c
#ifndef CALC_H
#define CALC_H

int add(int a, int b);

#endif
```

## 6-3. calc.c

関数の実際の処理を定義する。

```c
#include "calc.h"

int add(int a, int b)
{
    return a + b;
}
```

## 6-4. main.c

`add()` を呼び出す。

```c
#include <stdio.h>
#include "calc.h"

int main(void)
{
    int result = add(10, 20);

    printf("%d\n", result);

    return 0;
}
```

## 6-5. オブジェクトファイルの生成

```bash
gcc -c main.c -o main.o
```

```bash
gcc -c calc.c -o calc.o
```

それぞれのソースコードからオブジェクトファイルを生成する。

```text
main.c
  ↓
main.o

calc.c
  ↓
calc.o
```

## 6-6. リンク

```bash
gcc main.o calc.o -o main.exe
```

このコマンドでは、`main.o` と `calc.o` をリンクする。

```text
main.o ──┐
         ├── リンク ── main.exe
calc.o ──┘
```

`main.o` には `add()` を呼び出す処理がある。

`calc.o` には `add()` の実際の処理がある。

リンカは、`main.o` からの `add()` の参照を、`calc.o` にある定義と結びつける。

その結果、実行ファイルが完成する。

## 6-7. 重要ポイント

- 関数宣言は関数の使い方を知らせる。
- 関数定義は実際の処理を記述する。
- 別ファイルにある関数の処理は、リンクによって結びつけられる。
- 必要なオブジェクトファイルをリンク対象に指定する必要がある。

# 7. ヘッダーファイルとライブラリ

## 7-1. ヘッダーファイルとは

ヘッダーファイルは、関数の宣言、型定義、マクロなどを記述するファイル。

一般的な拡張子は `.h`。

例えば、自分で作成した `calc.h` も、C標準ライブラリの `stdio.h` もヘッダーファイルである。

## 7-2. 自作ヘッダーファイル

```c
#include "calc.h"
```

自分で作ったヘッダーファイルなどを取り込む際によく使用する。

## 7-3. 標準ライブラリのヘッダーファイル

```c
#include <stdio.h>
```

標準ライブラリが提供するヘッダーを取り込む際によく使用する。

`stdio.h` には、`printf()` などの関数の宣言が含まれている。

## 7-4. "" と <> の違い

どちらもヘッダーファイルを指定する方法。

違いは、主にヘッダーファイルを検索する場所と順序にある。

### ダブルクォーテーション

```c
#include "calc.h"
```

通常、現在のソースファイルがあるディレクトリなどを優先して探す。

### 山括弧

```c
#include <stdio.h>
```

コンパイラに設定された標準的なインクルード先などから探す。

※ 正確な検索場所や順序はコンパイラや開発環境によって異なる。

重要なのは、`""` と `<>` のどちらで指定しても、取り込む対象がヘッダーファイルであるということ。

---

# 8. ライブラリとは

## 8-1. ライブラリの役割

ライブラリとは、ほかのプログラムから再利用できるように用意された機能の集まり。

例えば、C標準ライブラリには `printf()` などの機能が用意されている。

```c
#include <stdio.h>

int main(void)
{
    printf("Hello\n");

    return 0;
}
```

このコードでは、`printf()` を使用して文字を出力している。

## 8-2. ヘッダーファイルとライブラリの違い

### ヘッダーファイル

関数の宣言などを提供する。

例：

`stdio.h` には `printf()` の宣言が含まれている。

コンパイラはその宣言を利用して、関数の呼び出し方を確認できる。

### ライブラリ

関数の実際の処理を提供する。

例：

標準ライブラリには、`printf()` の実際の処理が用意されている。

## 8-3. printf() が使用できるまで

```text
#include <stdio.h>
        ↓
プリプロセッサがヘッダーを取り込む
        ↓
コンパイラがprintf()の宣言を確認する
        ↓
アセンブラがオブジェクトファイルを生成する
        ↓
リンカがprintf()の参照を解決する
        ↓
実行ファイル完成
```

重要な点：

`stdio.h` を取り込んだからといって、`printf()` の実際の処理がソースコード内にコピーされるわけではない。

ヘッダーファイルには関数の宣言があり、ライブラリには実際の処理が用意されている。

## 8-4. 静的リンクと動的リンク

ライブラリの利用方法には、主に2種類ある。

### 静的リンク

必要なライブラリの処理を実行ファイルに組み込む方法。

### 動的リンク

実行時に共有ライブラリを利用する方法。

動的リンクの場合、ライブラリの処理がすべて実行ファイルにコピーされるわけではない。

## 8-5. GCCと標準ライブラリ

通常のGCCでは、必要なC標準ライブラリなどが自動的にリンクされる。

そのため、一般的なプログラムでは次のコマンドで実行ファイルを作成できる。

```bash
gcc main.c -o main.exe
```

# 9. コンパイルエラーとリンクエラー

## 9-1. コンパイルエラーとは

コンパイルの工程で発見されるエラー。

代表例：

- セミコロンの書き忘れ
- 文法の間違い
- 不正な型の使用
- 関数の引数の型や個数の不一致

ただし、型に関する問題は警告になる場合もある。

## 9-2. コンパイルエラーの例

```c
int main(void)
{
    int speed = 100

    return 0;
}
```

問題点：

```c
int speed = 100
```

セミコロン `;` がない。

正しいコード：

```c
int main(void)
{
    int speed = 100;

    return 0;
}
```

文法上の間違いなので、コンパイラがエラーを検出する。

# 10. 警告とエラーの違い

## 10-1. エラー

プログラムに問題があり、通常はそのまま処理を正常に完了できないことを示す。

## 10-2. 警告

問題の可能性があることを知らせる。

警告が出ても、コンパイル自体は成功する場合がある。

## 10-3. 型変換に関する警告

```c
int main(void)
{
    int speed = 10.5;

    return 0;
}
```

`10.5` は小数を持つ値。

一方、`speed` は `int` 型。

そのため、整数型への変換によって小数部分が切り捨てられ、`10` が保存される。

コンパイラや警告オプションによっては、この変換に対して警告が出る。

重要な点：

- エラーはプログラムを正常に処理できない問題を示す。
- 警告は問題の可能性を示す。
- 警告が出ても実行ファイルが生成される場合がある。
- 警告を無視せず、原因を確認することが重要。

※ 警告の詳しい種類と修正方法はDay35で学習する。

# 11. リンクエラー

## 11-1. リンクエラーとは

リンクの工程で発生するエラー。

C言語の文法が正しくても、リンクに失敗する場合がある。

今回学習した代表例は次の2種類。

1. 未定義参照（undefined reference）
2. 多重定義（multiple definition）

※ リンクエラーは、この2種類だけではない。

---

# 12. 未定義参照（undefined reference）

## 12-1. 未定義参照とは

プログラムが参照している関数や変数などの定義を、リンカが見つけられない場合に発生するエラー。

## 12-2. 例

main.c

```c
#include "calc.h"

int main(void)
{
    int result = add(10, 20);

    return 0;
}
```

calc.c

```c
#include "calc.h"

int add(int a, int b)
{
    return a + b;
}
```

それぞれのオブジェクトファイルを生成する。

```bash
gcc -c main.c -o main.o
gcc -c calc.c -o calc.o
```

しかし、次のコマンドを実行したとする。

```bash
gcc main.o -o main.exe
```

この場合、`calc.o` を指定していない。

そのため、リンカは `add()` の実際の定義を見つけられない。

結果として、未定義参照のリンクエラーが発生する。

## 12-3. 修正方法

```bash
gcc main.o calc.o -o main.exe
```

`calc.o` もリンク対象に指定する。

## 12-4. 重要ポイント

関数宣言が存在していても、実際の関数定義がリンク対象に存在しなければ未定義参照になる。

ヘッダーファイルを取り込むことと、関数の実際の処理をリンクすることは別である。

---

# 13. 多重定義（multiple definition）

## 13-1. 多重定義とは

同じ名前の外部リンケージを持つ関数や変数などが、複数のオブジェクトファイルで重複して定義されることによって発生するリンクエラー。

## 13-2. 例

main.c

```c
int get_speed(void)
{
    return 10;
}

int main(void)
{
    return get_speed();
}
```

control.c

```c
int get_speed(void)
{
    return 20;
}
```

どちらのファイルにも `get_speed()` が定義されている。

次のコマンドでリンクすると、

```bash
gcc main.c control.c -o main.exe
```

リンカが重複する定義を検出する。

結果として、多重定義のリンクエラーが発生する。

## 13-3. なぜエラーになるのか

同じ外部リンケージの名前に対して、重複した定義が存在するため。

リンカは、プログラム全体で使用される関数や変数の参照先を解決する。

同じ関数の外部定義が重複していると、多重定義としてエラーになる。

## 13-4. 修正方法

基本的には、外部へ公開する関数の定義を1か所にする。

例えば、

- control.c：関数の定義
- control.h：関数の宣言
- main.c：関数を呼び出す

という構成にする。

また、ファイル内部だけで使用する関数には `static` を付け、内部リンケージにする方法もある。

## 13-5. staticとの関係

Day33で学習したように、ファイルスコープの関数に `static` を付けると内部リンケージになる。

その関数名は別のソースファイルにある同名の `static` 関数とは別のものとして扱われる。

したがって、異なるファイル内に同名の `static` 関数があっても、それだけを理由に多重定義のリンクエラーにはならない。

---

# 14. コンパイルエラーとリンクエラーの比較

## コンパイルエラー

発生する工程：

コンパイル

主な原因：

- 文法の間違い
- 型の不適切な使用
- 宣言に関する問題

例：

```c
int speed = 100
```

セミコロンがない。

## リンクエラー

発生する工程：

リンク

主な原因：

- 関数や変数の定義を見つけられない。
- 同じ名前の外部定義が重複している。
- 必要なオブジェクトファイルやライブラリが不足している。

例：

```text
undefined reference to `add'
```

`add()` の定義が見つからない。

例：

```text
multiple definition of `get_speed'
```

`get_speed()` の定義が重複している。

## 重要な違い

コンパイルエラー：

ソースコードの文法や型などの問題。

リンクエラー：

オブジェクトファイルやライブラリの参照関係などの問題。

# 15. GCCコマンドの整理

## 15-1. アセンブリファイルを生成する

```bash
gcc -S main.c -o main.s
```

前処理とコンパイルを行い、アセンブリファイルを生成する。

## 15-2. オブジェクトファイルを生成する

```bash
gcc -c main.c -o main.o
```

前処理・コンパイル・アセンブルを行う。

リンクは行わない。

## 15-3. アセンブリファイルからオブジェクトファイルを生成する

```bash
gcc -c main.s -o main.o
```

アセンブリファイルをアセンブルし、オブジェクトファイルを生成する。

## 15-4. オブジェクトファイルをリンクする

```bash
gcc main.o calc.o -o main.exe
```

オブジェクトファイルなどをリンクして実行ファイルを生成する。

## 15-5. ソースコードから実行ファイルを生成する

```bash
gcc main.c calc.c -o main.exe
```

GCCが必要な前処理・コンパイル・アセンブル・リンクを実行する。

## 15-6. 警告オプションを付ける

```bash
gcc -Wall -Wextra main.c calc.c -o main.exe
```

- `-Wall`：多くの一般的な警告を有効にする。
- `-Wextra`：追加の警告を有効にする。
- `-o`：出力ファイル名を指定する。

`-Wall` はすべての警告を有効にするという意味ではない。

# 17. 組み込み開発との関係

組み込みソフトウェア開発でも、基本的な考え方は同じ。

例えば、STM32を使用した制御プログラムでは、次のようにファイルを分割することがある。

```text
main.c
sensor.c
sensor.h
control.c
control.h
```

それぞれのソースファイルをコンパイル・アセンブルし、オブジェクトファイルを生成する。

そしてリンカが、各オブジェクトファイルや必要なライブラリなどを結びつける。

組み込み開発では、さらにリンカスクリプトを利用して、プログラムやデータをFlashメモリ、RAMなどのどこに配置するかを指定する場合がある。

STM32などのマイコン向けには、通常、対象CPUに対応したクロスコンパイラを使用する。

例：

```text
arm-none-eabi-gcc
```

PC向けの実行ファイルとは異なり、マイコン向けにはELFファイルなどを生成し、必要に応じてBINファイルやHEXファイルに変換して書き込む。

今回学習したコンパイルとリンクの知識は、今後のSTM32開発にも直接つながる。

# 18. Day34の学習で理解できたこと

今回の学習では、ソースコードから実行ファイルが完成するまでの仕組みを理解した。

特に重要だったのは、次の点。

1. プリプロセッサは、`#include` や `#define` などの指示を処理する。

2. コンパイラは、C言語の文法や型などを確認し、アセンブリ言語に変換する。

3. アセンブラは、アセンブリ言語を機械語に変換し、オブジェクトファイルを生成する。

4. リンカは、オブジェクトファイルやライブラリを利用して関数や変数などの参照先を解決し、実行ファイルを生成する。

5. ヘッダーファイルには関数の宣言などがあり、ライブラリには関数の実際の処理が用意されている。

6. コンパイルエラーは、主に文法や型などに関する問題で発生する。

7. リンクエラーは、主に関数や変数の参照先の解決などに問題がある場合に発生する。

8. 未定義参照は、必要な定義が見つからない場合に発生する。

9. 多重定義は、同じ名前の外部定義が重複している場合に発生する。

# 19. 自分の言葉での最終まとめ

C言語のソースコードから実行ファイルが作られるまでには、前処理、コンパイル、アセンブル、リンクという工程がある。

最初にプリプロセッサが、`#include` や `#define`、`#ifdef`、`#ifndef` などの指示を処理する。

次にコンパイラが、C言語の文法や型などを確認し、必要に応じてエラーや警告を出しながら、アセンブリ言語へ変換する。

その後、アセンブラがアセンブリ言語を機械語に変換し、オブジェクトファイルを生成する。

最後にリンカが、複数のオブジェクトファイルや必要なライブラリを利用して、関数や変数の参照先を結びつけ、実行ファイルを完成させる。

また、ヘッダーファイルとライブラリは別の役割を持つ。

例えば、`stdio.h` には `printf()` の宣言が含まれており、実際の処理は標準ライブラリが提供する。

コンパイルエラーとリンクエラーについても区別できるようになった。

文法や型などの問題はコンパイルの工程で確認され、関数の未定義参照や多重定義などはリンクの工程で検出される。

これにより、C言語のコードがどのような工程を経て実行可能になるのかを理解できた。
